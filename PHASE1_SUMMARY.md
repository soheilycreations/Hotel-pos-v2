## 3. Database design highlights

- **Roles/permissions are tables, not enums** (`roles`, `permissions`, `role_permissions`) — the old system's `staff_role` enum and its enum→table conversions later (migrations 005/006/009) were exactly the fragility this avoids. `has_permission(text)` is the single gate used in every RLS policy and every RPC.
- **8 seeded roles**: owner, admin (both full access), manager (everything except staff/role management), reception, cashier, restaurant_staff, inventory_staff, accountant — each with a specific permission subset (see `seed_permissions_matrix.sql` for the exact matrix).
- **Optimistic locking**: `version int` on `bookings`, `restaurant_orders`, `inventory_items`, `staff_profiles`, `credit_accounts`. Every mutating RPC does `select ... for update` + compares `expected_version`, raising `CONCURRENT_MODIFICATION` on mismatch — verified live (see §4).
- **Order lifecycle state machine**: `order_status_transitions` is a data table + a `before update` trigger that rejects any status change not listed. 13 legal transitions seeded (`draft→open→submitted→preparing→ready→completed→settled`, plus cancellation/void/refund branches).
- **Stock floor + ledger**: `inventory_items.quantity_in_stock` has `check (>= 0)`; every change goes through `stock_movements` with a before/after snapshot. The column is **only** mutated by an internal function (`_apply_stock_movement`) with `EXECUTE` revoked from `authenticated`/`anon` — verified that a direct RPC call to it as a logged-in user is rejected outright.
- **Audit log**: append-only, RLS has no insert/update/delete policy for any role — the only writer is `log_audit_event()`, called from every correction/void/refund RPC.
- **Financial reversals** don't hack a negative `payments` row (that table's `amount > 0` check stays meaningful) — a refund posts a `credit_ledger` `REVERSAL` (credit sales) or a `cash_movements` `'out'` entry (cash/card sales), whichever matches how the original sale was paid.
- **RLS**: every table has RLS enabled; policies are permission-based (`has_permission('x')`), not role-name lists. Verified live that a role lacking a permission is blocked both at the RPC layer (raises `Missing permission: ...`) and at the raw-table level (RLS silently filters rows, e.g. a cashier querying `inventory_items` gets 0 rows).

## 4. RPC functions and what each closes from the audit

| Function | Purpose | Audit finding it fixes |
|---|---|---|
| `rpc_extend_stay` / `rpc_shorten_stay` | Move checkout date + post/reverse a charge atomically | #2 — old system could move the date without charging if the 2nd write failed |
| `rpc_check_in` / `rpc_check_out` | Status transition + room status + payment, one transaction | — |
| `rpc_settle_pos_order` | Locks the order **before** re-summing line items, computes totals, deducts recipe stock, posts payment/folio | #5 (race condition) + #2 (non-atomic settlement) |
| `rpc_void_pos_order` | Voids a pre-settlement order (no stock reversal needed — stock is only deducted at settlement) | — |
| `rpc_refund_order` / `rpc_refund_booking` | Reverses a settled sale via the correct ledger (credit or cash) | — |
| `_apply_stock_movement` (internal) / `rpc_adjust_stock` (public) | The only path that changes `quantity_in_stock`, enforces the `>= 0` floor | #3/#4 |
| `rpc_create_purchase` | Records a purchase + deducts... adds stock atomically per line item | replaces old one-off import scripts |
| `rpc_correct_settled_record` | The only way to edit a settled `bookings`/`restaurant_orders` row — requires a reason, requires `settled_records.correct`, always audit-logs before/after | #1 (no audit trail) |

**Design note surfaced during testing**: `rpc_settle_pos_order` needs to deduct stock as a side effect of a `pos.settle` permission check, not an `inventory.adjust` one (a cashier shouldn't need inventory-management rights just to ring up a sale). Fixed by splitting the mechanism (`_apply_stock_movement`, no permission check, unreachable directly) from the public entry point (`rpc_adjust_stock`, checks `inventory.adjust`) — internal RPCs call the former directly. This is exactly the kind of bug live testing was meant to catch.

## 5. Validation performed

- `npx tsc --noEmit` — clean, no errors.
- `npm run lint` (ESLint via Next 16) — clean, no warnings.
- `npm run build` — succeeds; initially showed a deprecation warning ("middleware" convention → "proxy") which I resolved via Next's own codemod (`middleware-to-proxy`) rather than leaving a warning in a fresh project; rebuilt clean afterward.
- **Live database verification** (this environment has no Docker, so I installed nothing new — Postgres 16 server binaries were already present on the box): stood up a throwaway local Postgres instance, added a minimal shim reproducing just the Supabase-platform pieces our SQL depends on (`auth.users`, `auth.uid()`, the `anon`/`authenticated`/`service_role` roles, the `supabase_realtime` publication), then replayed **all 10 migrations plus `seed.sql` from empty — all applied with zero errors**. This is a stronger check than static SQL review and is not something I could claim without actually doing it.
- **End-to-end RPC/RLS smoke tests** against that database (as an impersonated `authenticated` user per role, not as superuser), all passed:
  - Full booking lifecycle: create → check-in → extend stay (charge posted atomically) → check-out.
  - Stale `version` correctly rejected with `CONCURRENT_MODIFICATION`.
  - POS settlement with recipe-linked stock deduction: confirmed the exact gram amount was deducted and a matching `stock_movements` row was written.
  - A cashier (no `inventory.adjust`) successfully triggers stock deduction *through* `rpc_settle_pos_order`, but is blocked from calling `rpc_adjust_stock` or the internal function directly.
  - Over-ordering past available stock raises `INSUFFICIENT_STOCK` and the **whole settlement rolls back** — order stays `completed`, not stuck half-settled.
  - Void rejected for a settled order ("must be refunded"); refund correctly posts a `cash_movements` `'out'` row and flips status to `refunded`.
  - `rpc_correct_settled_record` correctly patches an allowed field, refuses a protected field (`id`), and its full audit trail (previous/new JSON + reason) was confirmed in `audit_log`.
  - RLS confirmed directly: a `reception`-role user querying `audit_log` gets 0 rows back, no error — the policy is filtering, not just the RPC layer.
- Test artifacts (shim + smoke-test SQL) live only in the session scratchpad, not in the project — they were throwaway verification tools, not part of the deliverable.

## 6. Assumptions and open issues for your review

1. **Next.js 16, not 15.** `create-next-app@latest` installed 16.3.3. The plan said "Next.js 15, bumped where sensible" — I read that as license to take the current stable version rather than pin to 15. Say the word if you want me to downgrade.
2. **No live Supabase project exists.** Everything above was verified against a stand-in shim, not real Supabase (no `auth.users` triggers, no PostgREST, no real GoTrue). Once you create a Supabase project and give me its URL + keys, Phase 2 should start by running these same migrations against it for a final confirmation before anything else.
3. **`rpc_correct_settled_record` is scoped to `bookings` and `restaurant_orders` only** (both have `version` columns). `booking_charges` and `expenses` are append-only ledgers by design (void/reversal-row pattern) and are deliberately not covered by this generic corrector — flag if you wanted them included too.
4. **Restaurant staff's `pos.orders.write` is coarse-grained** — it allows editing any field on an order, not just advancing its status. A narrower "kitchen can only change status" permission would need its own RLS policy; I judged that a Phase 4 (POS UI) refinement rather than a Phase 1 blocker.
5. **No `staff_profiles` seed row exists** — can't be created from SQL alone (needs a real `auth.users` row from Supabase Auth). `seed.sql` documents the two manual steps for creating your first Owner account once a real project exists.
6. **Email/SMTP is not configured anywhere** — `inviteStaffMember()` will silently fail to deliver until you configure SMTP on the Supabase project; `createStaffAccountWithTempPassword()` is there as a fallback but per your instruction is documented as secondary, not the default path.
7. **`hotel_settings` seeded with `hotel_name = 'Hotel Rawana'`, `timezone = 'Asia/Colombo'`, `currency = 'LKR'`** as defaults — change these in the migration or via the settings UI (Phase 6) if wrong.
